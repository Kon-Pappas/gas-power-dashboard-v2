# Decisions log

Format: **what** · *why* · alternatives rejected. The log starts on 26 October 2026, the day the alignment of this dashboard with the other hub dashboards began (house style as in live-greekpower and Flows; it is handled in its own thread, one phase at a time). Decisions marked *(existing)* were taken earlier, while the dashboard was built; they are written down here so that they are not lost.

| # | Decision | Why / what was rejected |
|---|---|---|
| D01 | *(existing)* **Cost model.** The theoretical cost of a unit is calculated **hour by hour** from its SCADA output: the position of the output between the unit's technical minimum and maximum (`PLANT_SPECS`) gives, by linear interpolation, that hour's efficiency and CO₂ factor; fuel cost = HGSIDA ÷ efficiency × MWh, CO₂ cost = tonnes × EUA price. Everything is calculated in `update_data.py` (`process_economics`) and stored in `daily_economics`; the page only shows it | Python calculates, the page only shows (hub rule). Linearity is the main simplifying assumption, written in the Methodology modal: real heat-rate curves are not linear and no per-unit curves are public. Rejected: one flat efficiency per unit and day (hides that a unit near its minimum is much less efficient). |
| D02 | *(existing)* **CO₂ price.** EUA price from oilpriceapi.com (`OILPRICE_API_KEY`), **one call per daily run** (`/v1/prices/latest`), stored under today's date; a backfill never calls the API. A weekend takes the last real price, marked `Estimated`; with no real price at all the value is €85.00, also marked. The page shows an *estimated* badge (Greek / English). 1 Jun – 23 Aug 2026 is the flat €85.00 estimate | Free tier: 50 requests a month, historical data not included; the older by-date lookup is not documented by the provider and gave shifted or repeated prices, so it was dropped. The price of the latest call may be the previous close, written under today's date: a known simplification. Rejected: scraping a market-data site for the missing history (terms of use forbid redistribution). |
| D03 | *(existing)* **Economics wait for HGSIDA.** The economics of a day are written only when a real HGSIDA > 0 exists for it; otherwise they wait for the next run. **Measured 26 Oct 2026 (git history of `main`, days 9–24 Oct):** the HGSIDA of day D first appears in the midday run of day **D+1**, between 11:00 and 12:42 (13:28–14:44 on 10–12 Oct), and never in the 07:07 run | HEnEx writes the file with the headers before the values: a day with HGSIDA = 0 gave a fuel cost of 0 and a fleet SRMC of 35 instead of 155 €/MWh (found 1 Oct 2026). Hence the midday run (D07). |
| D04 | *(existing)* **Generic constraints.** From the last sheet of the ISP2 file (*GenericConstraints*) only the unit and the hours are kept (`daily_gas_constraints`), for gas units on a **list of allowed prefixes**; Alouminio (co-generation, locked 24/7 output), Ptolemaida5 (lignite) and Agras (large hydro) are always left out. The MWh are the hourly SCADA of the unit inside those hours. A day without SCADA is left out of the Surplus chart and its totals; a day with SCADA and no constraint, or a low surplus, stays in, shown as zero | A list of what is allowed (not of what is excluded) keeps lignite and hydro out whatever appears in the file. ISP2 is the reference: ISP3 does not cover the whole day. The 56 rows of Elpedison that matched no SCADA unit were fixed in late September 2026 (they had added up as zero). |
| D05 | *(existing)* **Daily surplus** = the *Energy Surplus* row of the ISP2 file (column TOTAL, absolute value), stored in `daily_surplus` | It is a schedule, not a measurement; the Methodology says so. |
| D06 | *(existing)* **Unit classes** (H-Class, F-Class, Peakers) come from `thermal_efficiency` and decide the order and colour of the units in Daily Overview | One reading of the fleet by technology, as in the economics. |
| D07 | **Updates only from cron-job.org, daily at 07:06 and 13:00 Greek time (Europe/Athens, both jobs).** The workflow has no `schedule:`. The 13:00 run exists because of HGSIDA (D03) | **Measured 26 Oct 2026 (git history, 9–24 Oct):** the SCADA of day D was in `main` at the morning run (07:07–07:08) of D+1 on 15 of 16 days (22 Oct: 14:24). The GitHub `schedule` (`0 4 * * *`) drifts, and since the clock change of 25 Oct it would start at 06:00 Greek time, before the SCADA is published (~06:05). 13:00 leaves margin after the 11:00–12:42 appearances of D03. Rejected: keeping `schedule:` as a backup (it runs before the SCADA and adds commits); a third run (revisit if a late SCADA like 22 Oct repeats). |
| D08 | `data/meta.json` holds `fetched` (time of the run) and `next_update` (next scheduled run), both UTC with `Z` as in BESS and Flows (hub D06). The next run is computed in Athens time from `UPDATE_SCHEDULE` in `update_data.py`, so it is correct across the clock changes (tested 24–25 Oct 2026 and 27–28 Mar 2027). Its only writer is `update_data.py`, after the data file; the page shows both in Athens time and "-" if the file is missing | **Before (26 Oct 2026):** the page took the latest data date + "08:00" as *Last update* (showed 25/10/2026 08:00) and the next day + "08:00" as *Next* (26/10/2026 08:00): neither was the real run time. Python calculates, the page only shows. |
| D09 | Libraries pinned: **Tailwind 3.4.17** and **Chart.js 4.5.1** (from batch 2 the explicit file `chart.js@4.5.1/dist/chart.umd.min.js`, as in BESS); Actions `checkout@v5` and `setup-python@v6` | An unpinned CDN changes the page without any commit (hub rule). Versions as in the other hub dashboards. |
| D10 | The data files are written atomically (temporary file, then replace); the workflow runs one job at a time (`concurrency`) | A run that stops half way, or a manual backfill that overlaps the 07:06 or 13:00 run, must not leave a broken file or a failed push. |
| D11 | **Accent: blue, defined in one place. Green means only "complete / positive / ✓".** Owner's decision, 26 Oct 2026. The accent is implemented in batch 2 (D14); the data colours that clash with it, in Phase 2 (K04) | Blue is the colour assigned to Gas-Power in the hub (BESS emerald, Flows cyan, BigHydro violet, live-greekpower platinum). The data colours that today equal the accent (`#3b82f6` is class F, the HGSIDA line and the surplus bars) and the emerald of the efficiency line must change (Phase 2). |
| D12 | The Methodology modal now says that HEnEx publishes the HGSIDA of a day **the following day, by around midday** (it said "later in the day"), and that the page is updated twice a day | The first wording was written before the measurement of D03. |
| D13 | `README.md` and `docs/` (this file, `KNOWN_ISSUES.md`, `ROADMAP.md`) start with batch 1, in English as the live page. Codes **H** (hub-wide issues) and **C** (conventions) are the same in every repository; every measurement is written with its number and date | A decision can be checked later. Same structure as BESS and Flows. |
| D14 | **The accent is defined in one place**, at the top of `index.html`: `window.ACCENT = { 200: '#bfdbfe', 300: '#93c5fd', 400: '#60a5fa', 500: '#3b82f6', 600: '#2563eb' }` (blue, the Tailwind blues of before), given to Tailwind as `acc-200 … acc-600` and to the CSS as `--acc`. 28 decorative uses of `blue-*` became `acc-*` (21 in `index.html`, 5 in `dashboard.js`, 2 in `data.js`): the title, the spinner and bar of the loading overlay, the active tab, the active GR \| EN button, hovers, focus borders, the icon of the Methodology window. The two header values follow BESS and Flows: *Last update* `acc-300`, *Next update* neutral (`slate-200`) instead of green. The Methodology headings and the Short / Detailed switch were emerald (copied from BESS, where emerald is the accent) and are now accent. **Four blues stay, because they are data colours:** the HGSIDA value, the *Max Efficiency* card with its bar and the monthly surplus value (Phase 2, K04) | Owner's decision D11. The shade 600 is an addition to the hub's 200–500: it is the filled background of the active tab and button, and keeping it means the page looks the same; Phase 3 may remove it. **Measured 26 Oct 2026 in Chromium:** of 706 elements, the colours of only 7–8 changed (the two header values, the switch and the Methodology headings), and no size changed. Rejected: replacing every blue, which would have turned data into decoration. |
| D15 | **The language is remembered** in `localStorage` under the common key `kp_lang` (the same origin for the whole hub, so the choice follows the visitor from page to page). English is the default; only `el` and `en` are accepted; if the browser blocks storage (private browsing) the page works as before. As in BESS, `setLang` writes the key, so a first visit stores `en`. **Tested 26 Oct 2026:** clean browser, stored `el`, choosing and reloading in both directions, an invalid value, blocked storage; zero console errors | Same behaviour as BESS D04 and Flows. Known limit until K01 is done: the loading overlay is still in English while the data load, whatever the saved language. Rejected: choosing the language from the browser settings (the hub is English by default). |
| D16 | **The day-ahead prices (`dam_mcp_hourly`) are removed:** the collection (`process_dam`), the key in `historical.json` and its loading in the page. The first run after the change deletes the key from the file (148 days). The Methodology now says what the page does: *constraint-driven generation* is the SCADA output of a gas unit in the hours the ISP2 lists it under a Generic Constraint; prices are not compared. Owner's decision (option B), 26 Oct 2026 | Nothing used it: the page loaded it into `rawData.mcpHourly`, `dashboard.js` never read it and the economics do not use it, while the Methodology said that a unit running when the MCP is below its fuel cost is shown as constraint-driven, which the code never calculated. **Measured 26 Oct 2026 (1–24 Oct):** the price view (hours in which the MCP is below the unit's average SRMC, SCADA hour *h* matched with MCP hour *h*−1, hour 1 left out) gives 214,213 MWh, 17.1 % of the gas generation; the constraint view gives 57,880 MWh, 4.6 %; their daily correlation is 0.64: they are two different quantities. File: 227 → 211 KB gzip (−7.3 %). **Reversible:** the HEnEx files stay online and the history can be fetched again. A price view, if wanted later, comes as a separate quantity with its own name, together with the CET alignment (HEnEx hours are CET: the repeated hour of 25 Oct is written 02:00 twice) and the fix for 25 hours (the `ResultsSummary` of 25 Oct has 100 quarter-hours and the old parser kept 96). |
| D17 | **The SCADA hours come from the calendar, not from a fixed 24.** `hours_in_day(date)` gives the hours of the Greek day (24; 25 on the last Sunday of October; 23 on the last Sunday of March) and the script reads that many hour columns of the file's header (`find_hour_columns`); the key of the daily file records `01:00 … 25:00`. **The sum of the hours is checked against the file's own SUM column** (a warning in the log if they differ by more than 1 MWh). The economics use all the hours of a record, and the Surplus tab reads an hour by its name (`"05:00"`), no longer by its position in the row | **Measured 26 Oct 2026 on the real SCADA file of 25 Oct:** the file has 25 hour columns and the old script read 24: the fleet was stored as 70,318 MWh against 73,419 in the file (its SUM column agrees), 3,101 MWh or 4.22 % short; the cost of that day would have been 4.19 % low. **The template has 25 hour columns every day since mid-June** (11 Jun: 24 + SUM; 18 Jun: 25 + SUM, the 25th all zeros), so the number of hours cannot be read from the header; the first version of this fix did that and reported 25 hours for 18 Jun, which the regression test caught. **Tests:** 11 and 18 Jun (24 hours): the stored result is byte for byte the same as before; 25 Oct: 25 hours, 73,419 MWh, equal to the SUM column; a synthetic 23-hour day made from the real file: 23 hours, correct total, the SUM column is not read as an hour; a tampered SUM, a 23-hour day with a 25-hour SUM and a file without the header give a warning. On the page, a synthetic 23-hour day gave 2,600 MWh with the old reading by position (300 correct plus the daily total read as hour 24) and 300 with the new one; for the five real months the page gives the same numbers as before. No other day in the data (1 Jun – 25 Oct) is a clock-change day. The 25 Oct record in the repository is repaired by the next runs (the SCADA of the last 10 days is read again): the fix has to be online by **4 Nov**. |
